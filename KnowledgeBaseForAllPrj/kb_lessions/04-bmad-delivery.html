BMAD-compatible planning

Adapter BMAD trong repo chọn lượng planning vừa đủ, giữ liên kết từ problem đến evidence và giao implementation cho các skill chuyên biệt. Đây là compatibility layer, không phải official BMAD runtime.

01. Why

Không phải change nào cũng cần một bộ ceremony giống nhau.

Thiếu planning làm change rủi ro mất dependency và acceptance. Quá nhiều planning cho typo fix lại gây latency, stale artifact và chi phí review. Right-sizing chọn đường đi theo blast radius, uncertainty, dependency, migration và approval.

PathKhi dùngArtifact tối thiểu
DirectNhỏ, cục bộ, reversible, acceptance rõTask + evidence; vẫn phải test
QuickMột feature/change vừa, ít dependencyTech spec + acceptance + risk
EpicNhiều story/workstream có dependencyEpic map + story inventory + readiness
ProjectMulti-domain, architecture/migration/governance lớnProblem/requirements/architecture + phased delivery
02. Classification

Planning path là quyết định có evidence.

IntentOutcome + constraints
Assessrisk, scope, uncertainty
Choose pathDirect/Quick/Epic/Project

Ví dụ

Direct

Sửa broken link

Một file docs, không đổi behavior, validator là acceptance evidence.

Epic

Webhook idempotency

Schema, API, worker, migration, observability và rollback tạo nhiều story phụ thuộc.

Reclassify khi fact đổi. Một “small change” phát hiện cần data migration phải quay lại classification; không cố giữ Direct chỉ vì đã bắt đầu.
03. Artifact contracts

Traceability nối “vì sao” với “đã chứng minh thế nào”.

Problem / goal
  → requirement IDs + acceptance criteria
  → architecture decisions + risks
  → epic / story IDs + dependencies
  → implementation commits + tests
  → verification evidence + retrospective

Artifact có stable ID và version. Story không chỉ là một đoạn văn: nó khai báo dependency, read/write scope, acceptance, test evidence và owner. Khi requirement đổi, impact analysis lần theo relation thay vì đoán bằng filename.

04. Readiness gate

Gate không chấm văn hay; gate tìm thiếu sót gây delivery thất bại.

ResultÝ nghĩaHành động
PASSCoverage, dependency, acceptance, ownership đủĐược compile execution plan
CONCERNSCó gap đã biết, có disposition/owner rõOwner chấp nhận hoặc sửa trước build
FAILMissing critical input, contradiction hoặc unsafe migrationDừng; không fan-out implementation

Các check deterministic chạy trước: schema/version, ID uniqueness, dependency cycle, story coverage, write conflict, completion contract. Model review chỉ bổ sung semantic nuance.

05. Story lifecycle

Story đi qua state có điều kiện, không nhảy thẳng từ draft sang done.

Draftgoal + scope
Readyacceptance + dependencies
In progressbounded write scope
Reviewtests + findings
Acceptedverification evidence

Parent epic chỉ complete khi child completion contract thỏa, integration đã chạy và verifier độc lập chấp nhận. “Các agent đều finished” không đủ.

06. Flow thực tế

Thêm idempotent webhook processing.

  1. Classify Epic: đổi schema + worker + API + metrics + rollback.
  2. Artifacts: requirement định nghĩa duplicate semantics; ADR chọn idempotency key; epic map nêu dependencies.
  3. Slice stories: database constraint trước repository; repository trước worker; docs/observability có thể song song khi contract đã freeze.
  4. Readiness: phát hiện thiếu retention policy → CONCERNS; owner disposition trước build.
  5. Execute waves: mỗi story gọi $gen-code; review read-only chạy sau từng implementation artifact.
  6. Join: integration test replay cùng event, migration rehearsal và rollback evidence.
  7. Retro: lesson nằm ở episodic memory; reusable rule vào promotion queue.
07. Evidence-backed retrospective

Học từ trace, không viết lore.

Retrospective liên kết planned vs actual, test/incident trace, decision và outcome. Nó phân loại process issue, knowledge gap hay one-off event. Chỉ claim tái sử dụng có provenance mới thành promotion candidate.

Anti-pattern: tự động biến mọi “what went well” thành shared standard. Survivorship bias và bối cảnh dự án có thể tạo policy sai cho toàn KB.

Self-check

Ba câu kiểm tra

1. Direct path có được bỏ test?

Xem đáp án

Không. Nó giảm artifact/ceremony, không giảm acceptance và evidence.

2. Readiness CONCERNS có nghĩa là auto-pass?

Xem đáp án

Không. Concern phải có disposition và authority chấp nhận; critical gap vẫn là FAIL.

3. BMAD adapter có thay thế gen-code/review-code?

Xem đáp án

Không. Nó route planning/delivery; skill chuyên biệt vẫn sở hữu implementation và review.
