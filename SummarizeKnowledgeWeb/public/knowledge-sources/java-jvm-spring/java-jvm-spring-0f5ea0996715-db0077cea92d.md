# Đáp án — JVM, Spring và Hibernate Middle & Senior

> Đây là khung chấm phỏng vấn chuyên sâu. Câu trả lời mạnh phải chỉ ra cơ chế, bằng chứng quan sát được và quyết định phù hợp workload thay vì chỉ kể tên annotation/tool.

## 1. Bytecode, class loading và reflection

### JVM-001 [Middle] Từ source Java đến lúc method chạy qua những bước compile, load, link, initialize và execute nào; bytecode mang lại tính portable ra sao?

**Kết luận:** `javac` biến source thành class file/bytecode theo JVM specification; JVM load class, link (verify, prepare, resolve), initialize static state rồi interpreter/JIT thực thi.

**Lập luận:** Verify kiểm tra bytecode type/control-flow; prepare cấp static storage/default; resolution đổi symbolic reference; `<clinit>` chạy khi active use. Bytecode portable trên JVM tương thích, còn JIT biên dịch hot code sang machine code theo CPU/runtime profile.

**Pitfall/trade-off:** “Write once run anywhere” không xóa khác biệt OS, charset, native library hay JDK version. Compile target cao hơn runtime gây `UnsupportedClassVersionError`.

**Mức kỳ vọng:** **Middle:** kể đúng pipeline. **Senior:** nối class-file compatibility, lazy resolution và tiered JIT với startup/warmup.

### JVM-002 [Senior] Mô hình parent delegation của class loader hoạt động thế nào; khi nào custom class loader, plugin container hoặc app server gây `ClassNotFoundException`, `NoClassDefFoundError` hay `ClassCastException` dù tên class giống nhau?

**Kết luận:** Class identity là cặp `(binary name, defining class loader)`. Delegation thường hỏi parent trước để tránh duplicate core/shared class, nhưng plugin/container có thể child-first hoặc isolation riêng.

**Lập luận:** `ClassNotFoundException` thường từ yêu cầu load tường minh không tìm thấy; `NoClassDefFoundError` khi runtime cần definition từng có lúc compile hoặc initialization trước đã fail; cùng tên do hai loader định nghĩa vẫn là hai type khác, cast thất bại.

**Pitfall/trade-off:** Context class loader sai làm SPI không thấy provider. Loader leak xuất hiện khi thread/static/cache giữ class/plugin cũ. Không chữa bằng copy JAR ngẫu nhiên.

**Mức kỳ vọng:** **Middle:** phân biệt ba lỗi. **Senior:** đọc loader chain/code source, phát hiện duplicate và thiết kế API shared ở parent boundary.

### JVM-003 [Middle] Phân biệt thời điểm load, verify, prepare, resolve và initialize class; truy cập `static final` compile-time constant có kích hoạt initialization không?

**Kết luận:** Load tạo `Class`; link gồm verify/prepare/resolve; initialize chạy static initializer/assignment. Compile-time constant thường được inline vào caller nên truy cập không kích hoạt class khai báo.

**Lập luận:** Active use như `new`, gọi static method, đọc/ghi static non-constant hoặc reflection kích hoạt initialization; initialize subclass trước hết initialize superclass. Resolution có thể lazy.

**Pitfall/trade-off:** Đổi giá trị constant trong thư viện mà không recompile consumer có thể giữ giá trị cũ. `<clinit>` lỗi làm class unusable tiếp theo và thường hiện `NoClassDefFoundError`.

**Mức kỳ vọng:** **Middle:** phân biệt load và init. **Senior:** dự đoán initialization order/deadlock và binary constant inlining.

### JVM-004 [Senior] Bytecode instruction, operand stack, local variable table và stack frame phối hợp để thực thi method như thế nào; điều này giúp đọc stack trace/decompile ra sao?

**Kết luận:** Mỗi invocation có frame chứa locals, operand stack và metadata; instruction nạp locals/constant lên stack, thao tác rồi store/call/return.

**Lập luận:** Descriptor định slot/kiểu; object method có `this` ở local 0. `invokevirtual`, `invokeinterface`, `invokestatic`, `invokespecial`, `invokedynamic` mang dispatch khác nhau. Line number/local variable tables là debug metadata, có thể thiếu.

**Pitfall/trade-off:** Decompiler tái dựng source gần đúng, không phải source gốc; synthetic bridge/lambda/try-finally làm stack trace lạ. JIT inline không làm Java stack semantics biến mất nhưng profile/native stack cần giải mã.

**Mức kỳ vọng:** **Middle:** đọc `javap -c`. **Senior:** suy call/exception path từ bytecode và nhận diện synthetic/invokedynamic.

### JVM-005 [Senior] Reflection, method handle và generated bytecode/proxy khác nhau về type safety, access check, warmup và hiệu năng; framework nên chọn cách nào?

**Kết luận:** Reflection linh hoạt/dễ dùng nhưng type check muộn; method handle là typed invocation primitive JIT-friendly; generated class/proxy có call site trực tiếp hơn nhưng tăng build/startup/metaspace complexity.

**Lập luận:** Cache lookup/metadata quan trọng hơn lặp `getMethod`. Method handle có thể adapt signature và inline sau warmup. Bytecode generation hữu ích hot serialization/DI path, nhưng cần loader lifecycle và module access đúng.

**Pitfall/trade-off:** Microbenchmark cũ về reflection có thể không đúng JDK mới. `setAccessible` bị JPMS giới hạn; generation quá nhiều gây metaspace/class-loader leak.

**Mức kỳ vọng:** **Middle:** hiểu reflection cost/access. **Senior:** chọn theo hotness, startup/AOT, loader/module và benchmark end-to-end.

### JVM-006 [Middle] Annotation có retention/source target khác nhau thế nào; vì sao annotation processor compile time khác reflection runtime?

**Kết luận:** `SOURCE` biến mất sau compile; `CLASS` nằm trong class file nhưng không bắt buộc thấy runtime; `RUNTIME` đọc được qua reflection. `@Target` giới hạn vị trí dùng.

**Lập luận:** Annotation processor chạy trong compilation, đọc model source/type và sinh file/code/diagnostic; reflection chạy trên class đã load và chỉ thấy metadata runtime. Type-use annotation có thể phục vụ checker/tooling.

**Pitfall/trade-off:** Gắn `RUNTIME` không tự kích hoạt behavior; framework phải scan/process. Processor làm build chậm hoặc không incremental nếu viết sai; reflection scan tăng startup.

**Mức kỳ vọng:** **Middle:** chọn retention/target đúng. **Senior:** cân nhắc compile-time generation với runtime discovery/AOT.

### JVM-007 [Senior] JPMS module path giải quyết encapsulation/dependency nào so với classpath; split package, automatic module và reflective access gây khó khăn gì?

**Kết luận:** JPMS khai báo `requires/exports`, tạo reliable configuration và strong encapsulation; classpath gần như một namespace phẳng, dễ duplicate/shadow dependency.

**Lập luận:** `exports` cho compile/runtime access; `opens` cho deep reflection. Module path không cho split package trong resolved modules. Automatic module giúp migration nhưng tên/exports rộng có thể không ổn định.

**Pitfall/trade-off:** `--add-opens` là cầu nối vận hành, không phải thiết kế dài hạn. Framework reflection/proxy/resource loading cần module metadata đúng; modularization có chi phí migration.

**Mức kỳ vọng:** **Middle:** hiểu export/open. **Senior:** lập migration strategy, API module boundary và tránh phụ thuộc automatic-name mong manh.

### JVM-008 [Senior] Hãy chẩn đoán lỗi linkage sau khi nâng version thư viện (`NoSuchMethodError`, `AbstractMethodError`): binary compatibility và dependency convergence liên quan thế nào?

**Kết luận:** Code compile với một API nhưng runtime load class phiên bản không tương thích. `NoSuchMethodError` thiếu method descriptor; `AbstractMethodError` thường interface/supertype đổi mà implementation runtime không cung cấp method.

**Lập luận:** In dependency tree, tìm version được resolve, duplicate JAR và code source thực của class; so descriptor bằng `javap`. Maven nearest mediation/Gradle resolution có thể chọn transitive version khác compile expectation.

**Pitfall/trade-off:** Clean/rebuild không sửa runtime image chứa JAR cũ. Exclusion tùy tiện có thể chuyển lỗi. Dùng BOM/constraints, convergence check và integration test artifact đóng gói.

**Mức kỳ vọng:** **Middle:** kiểm tra dependency tree. **Senior:** chứng minh class nào/loader/JAR nào, đánh giá semantic/binary compatibility và khóa graph.

## 2. JIT, memory, GC và diagnostics

### JVM-009 [Middle] Heap, thread stack, metaspace, code cache và direct/native memory chứa gì; loại lỗi cạn bộ nhớ tương ứng được biểu hiện thế nào?

**Kết luận:** Heap chứa object/array; mỗi thread có stack frame; metaspace chứa class metadata; code cache chứa compiled code; native/direct còn có buffer, JVM structure và library allocation.

**Lập luận:** Heap/metaspace/direct buffer có thông báo OOME khác; stack sâu gây `StackOverflowError`; quá nhiều thread có thể “unable to create native thread”. Process RSS có thể vượt xa `-Xmx`.

**Pitfall/trade-off:** Heap dump không giải thích mọi native leak. Tăng `-Xmx` trong container có thể làm OOMKilled vì thiếu headroom cho non-heap.

**Mức kỳ vọng:** **Middle:** map vùng nhớ với symptom. **Senior:** lập memory budget tổng và dùng NMT/OS metric/class histogram đúng vùng.

### JVM-010 [Senior] Escape analysis, scalar replacement, inlining và deoptimization của JIT có thể làm benchmark/stack trace khác trực giác ra sao?

**Kết luận:** JIT dùng profile để inline/optimize; object không escape có thể bị scalar replace/eliminate; giả định profile sai thì deopt về code ít tối ưu hơn.

**Lập luận:** Allocation thấy trong source có thể không tồn tại ở machine code; method call có thể inline nhiều tầng. Uncommon path/type mới làm deoptimization và latency spike trong warmup. JVM vẫn có thể reconstruct logical state cho exception/debug tại safepoint.

**Pitfall/trade-off:** Escape analysis là optimization, không phải contract. Benchmark không consume result bị loại; profile production khác test khiến inlining decision khác.

**Mức kỳ vọng:** **Middle:** hiểu warmup/JIT. **Senior:** đọc compilation/JFR event và thiết kế benchmark không phụ thuộc optimization giả tạo.

### JVM-011 [Middle] Young/old generation và generational hypothesis hoạt động ra sao; allocation, promotion và stop-the-world pause liên hệ thế nào?

**Kết luận:** Phần lớn object chết trẻ, nên collector thu young thường xuyên; survivor sống đủ lâu được promote/đặt ở old. Allocation nhanh thường qua TLAB/bump pointer.

**Lập luận:** Young collection thường STW để trace/copy live object; pause phụ thuộc live set/reference processing hơn chỉ heap size. Allocation rate cao tăng tần suất; promotion pressure làm old tăng và có thể dẫn tới mixed/full collection.

**Pitfall/trade-off:** “Tạo object luôn đắt” không đúng; giữ object sống lâu mới có thể đắt hơn. Tăng young gen giảm frequency nhưng mỗi pause/copy có thể lớn.

**Mức kỳ vọng:** **Middle:** đọc basic GC metric. **Senior:** liên hệ allocation/live-set/promotion với pause và tuning dựa log.

### JVM-012 [Senior] So sánh G1, ZGC và Shenandoah theo mục tiêu pause, throughput, heap size và overhead; vì sao không có collector tốt nhất cho mọi workload?

**Kết luận:** G1 là region-based cân bằng throughput/pause; ZGC và Shenandoah chuyển nhiều marking/relocation sang concurrent để pause rất thấp, đổi lại CPU/memory barrier overhead và yêu cầu headroom.

**Lập luận:** Chọn theo JDK/platform support, heap, allocation, latency SLO, CPU budget và container limit. Collector concurrent vẫn có safepoint/STW phase; nếu allocation vượt tốc độ reclaim vẫn gặp stall/failure.

**Pitfall/trade-off:** Chọn collector theo benchmark blog là sai. Heap nhỏ/throughput batch có thể không hưởng low-pause collector; tuning quá nhiều flag cũ cản ergonomics.

**Mức kỳ vọng:** **Middle:** nêu mục tiêu khác nhau. **Senior:** chạy controlled load, đọc pause/concurrent-cycle/headroom và chọn theo SLO/cost.

### JVM-013 [Senior] Hãy phân biệt memory leak Java, allocation pressure và native memory leak; dùng heap dump, class histogram, NMT và GC log để xác nhận thế nào?

**Kết luận:** Java leak là object còn reachable ngoài ý muốn; allocation pressure là churn cao nhưng thu được; native leak tăng RSS ngoài managed heap.

**Lập luận:** GC log/histogram theo thời gian phân biệt used-after-GC tăng với churn. Heap dump dùng dominator/retained path tới GC root. NMT baseline/diff phân loại JVM native category; nếu không thấy, dùng OS/native profiler và kiểm tra JNI/library.

**Pitfall/trade-off:** Heap dump có pause/disk/sensitive data. RSS không giảm không luôn là leak vì allocator/committed memory giữ pages. Một snapshot không chứng minh trend.

**Mức kỳ vọng:** **Middle:** lấy histogram/log an toàn. **Senior:** triangulate heap/NMT/OS, tìm ownership root và xác nhận sau fix.

### JVM-014 [Middle] Strong, soft, weak và phantom reference khác nhau thế nào; vì sao soft reference thường không phải lựa chọn cache production tốt?

**Kết luận:** Strong giữ object; weak được clear khi chỉ còn weak; soft được JVM giữ/clear theo memory policy; phantom được enqueue sau khi object không còn khả năng truy cập để quản lý cleanup hậu kỳ.

**Lập luận:** `WeakHashMap` weak ở key và phù hợp metadata gắn lifecycle key, không phải cache tùy ý. Phantom + `ReferenceQueue`/Cleaner quản lý native resource fallback, nhưng explicit close vẫn tốt hơn.

**Pitfall/trade-off:** Soft cache có eviction không dự đoán, dễ giữ heap đến lúc pressure rồi tạo storm reload. Cache production cần bound theo size/weight/time và metric.

**Mức kỳ vọng:** **Middle:** phân biệt reachability. **Senior:** chọn explicit lifecycle/cache policy và tránh cleanup dựa GC cho resource khan hiếm.

### JVM-015 [Senior] GC log cho thấy old-gen tăng dần và full GC không thu hồi: hãy lập kế hoạch điều tra dominator, retained size, GC root và class-loader leak.

**Kết luận:** Xác nhận trend sau major/full GC, lấy heap dump gần trạng thái cao, xếp dominator theo retained size rồi lần shortest path tới GC root/owner.

**Lập luận:** So nhiều histogram/dump để tìm class tăng. Với loader leak, xem nhiều instance loader cũ giữ class/static/cache/thread/ThreadLocal, JDBC driver hoặc executor. Kết nối object với business cardinality và lifecycle deploy.

**Pitfall/trade-off:** Dominator lớn có thể là cache chủ đích; shallow size không nói retention. Dump khi OOM có thể thất bại thiếu disk và chứa secret, cần chuẩn bị trước.

**Mức kỳ vọng:** **Middle:** đọc dominator/path-to-root. **Senior:** xác định owner/lifecycle, reproduce và chứng minh retained set ổn định sau sửa.

### JVM-016 [Senior] Safepoint và stop-the-world khác nhau thế nào; time-to-safepoint dài có thể đến từ đâu và quan sát bằng JFR/log thế nào?

**Kết luận:** Safepoint là trạng thái JVM biết/điều khiển thread để làm operation toàn cục; STW là khoảng application threads bị dừng. Pause tổng có thể gồm thời gian đưa threads tới safepoint và operation tại đó.

**Lập luận:** Thread chạy native/critical section hoặc code thiếu poll trong tình huống/JDK cụ thể có thể chậm rendezvous. JFR và safepoint/unified log tách reason, synchronization time và cleanup/operation time.

**Pitfall/trade-off:** Gán mọi pause cho GC bỏ sót deoptimization, class redefinition, biased-lock legacy hay safepoint khác. Flag/event khác theo JDK, cần kiểm tra phiên bản.

**Mức kỳ vọng:** **Middle:** hiểu STW không chỉ full GC. **Senior:** correlate safepoint event với native stack/JDK issue và sửa dựa evidence.

### JVM-017 [Middle] Thread dump cho biết các trạng thái `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING` gì; cách tìm deadlock và lock contention là gì?

**Kết luận:** `BLOCKED` chờ monitor entry; `WAITING/TIMED_WAITING` chờ condition/join/park có hoặc không timeout; `RUNNABLE` gồm đang CPU hoặc một số native I/O theo JVM state mapping.

**Lập luận:** Xem stack, “waiting to lock” và “locked” identity để dựng owner/waiter; deadlock là cycle, JVM thường in phần phát hiện. Lấy nhiều dump cách nhau để phân biệt transient với hotspot kéo dài.

**Pitfall/trade-off:** Nhiều WAITING trong pool idle là bình thường. Thread dump không trực tiếp cho CPU percentage; correlate OS/JFR/metric.

**Mức kỳ vọng:** **Middle:** đọc state/lock owner. **Senior:** gom signature, quantify contention và nối với code/resource pool.

### JVM-018 [Senior] Thiết lập observability JVM tối thiểu cho production gồm metric, GC log, JFR, tracing và alert nào; làm sao giữ overhead/chứa dữ liệu nhạy cảm trong kiểm soát?

**Kết luận:** Theo dõi heap/non-heap/pool, allocation/GC pause, thread/CPU, class loading, safepoint, executor/connection queue và app SLI; bật GC log rotation, JFR continuous bounded và distributed trace sampling.

**Lập luận:** Alert theo user impact/SLO và trend headroom, không chỉ raw threshold. Giữ runbook để lấy dump/profile, đồng bộ timestamp/correlation ID. JFR ring buffer cho pre-incident context với overhead thấp khi cấu hình phù hợp.

**Pitfall/trade-off:** High-cardinality label phá backend; stack/argument/request có PII/secret. Full tracing/profile liên tục tăng cost, cần sampling, retention, access control và redaction.

**Mức kỳ vọng:** **Middle:** dashboard/GC log cơ bản. **Senior:** thiết kế telemetry budget, SLO alert và incident workflow có kiểm chứng overhead/privacy.

## 3. Spring IoC, lifecycle, AOP và proxy

### JVM-019 [Middle] IoC/Dependency Injection đem lại lợi ích gì; constructor injection hơn field injection ở điểm nào về invariant, testability và circular dependency?

**Kết luận:** Container quản lý construction/wiring/lifecycle; constructor injection làm dependency bắt buộc, object hợp lệ ngay khi tạo, field có thể final và test không cần reflection/container.

**Lập luận:** Dependency hiện rõ trong signature; constructor quá dài báo class có thể quá nhiều trách nhiệm. Circular constructor dependency fail sớm, giúp lộ thiết kế vòng.

**Pitfall/trade-off:** DI không có nghĩa mọi value/object phải là bean. Optional dependency hoặc nhiều implementation cần qualifier/config rõ; service locator chỉ che coupling.

**Mức kỳ vọng:** **Middle:** dùng constructor injection. **Senior:** thiết kế module/ports, ownership lifecycle và dùng cycle như tín hiệu refactor.

### JVM-020 [Senior] Spring tạo và khởi tạo bean qua những giai đoạn nào; `BeanFactoryPostProcessor`, `BeanPostProcessor`, init callback và proxy chen vào lifecycle ở đâu?

**Kết luận:** Container đọc bean definitions; factory post-processor sửa metadata trước instantiate; bean được construct/populate/aware callbacks, post-process trước init, init, rồi post-process sau init thường có thể trả proxy.

**Lập luận:** `BeanDefinitionRegistryPostProcessor` còn đăng definition. Init qua `@PostConstruct`, `InitializingBean` hoặc configured method có ordering tương ứng; destruction callback chạy khi context đóng cho scope hỗ trợ. Một số auto-proxy creator cần early reference cho cycle.

**Pitfall/trade-off:** Gọi external I/O lâu trong init làm startup kẹt; truy cập bean quá sớm có thể bỏ post-processing/proxy. Không dựa vào ordering ngầm giữa processors.

**Mức kỳ vọng:** **Middle:** biết init/destroy. **Senior:** chẩn đoán proxy sớm, post-processor order và startup lifecycle.

### JVM-021 [Middle] Scope singleton của Spring có nghĩa gì và có tự thread-safe không; state mutable trong singleton controller/service gây bug nào?

**Kết luận:** Singleton là một bean instance cho mỗi bean definition trong `ApplicationContext`, không phải singleton toàn JVM và không tự thread-safe.

**Lập luận:** Controller/service nhận concurrent requests; field request-specific/counter/list mutable gây race và leak dữ liệu giữa user. Giữ service stateless, đưa state vào local/DB/cache thread-safe hoặc synchronize đúng invariant.

**Pitfall/trade-off:** `final` dependency không làm dependency đó thread-safe. Request/session scope có proxy/lifecycle cost và không thay thế thiết kế state rõ.

**Mức kỳ vọng:** **Middle:** phát hiện mutable singleton bug. **Senior:** phân tích publication, scope proxy và consistency của shared state.

### JVM-022 [Senior] Circular dependency có thể được Spring xử lý hoặc không xử lý trong trường hợp nào; vì sao giải pháp bền vững thường là tách trách nhiệm thay vì dùng `@Lazy`?

**Kết luận:** Constructor cycle không thể tạo object đầu tiên; một số setter/field cycle từng được giải qua early reference tùy cấu hình, nhưng có rủi ro bean chưa hoàn chỉnh/proxy và Spring Boot hiện đại thường không khuyến khích/cho phép mặc định.

**Lập luận:** `@Lazy` trì hoãn một cạnh bằng proxy nhưng coupling logic vẫn vòng, làm lifecycle/test/transaction khó đoán. Tách orchestration, domain event hoặc interface/port để dependency graph có hướng.

**Pitfall/trade-off:** Bật lại circular references che kiến trúc xấu; refactor event có thể đổi consistency/ordering nên phải explicit.

**Mức kỳ vọng:** **Middle:** nhận biết constructor cycle. **Senior:** vẽ dependency graph và chọn refactor giữ transaction/invariant.

### JVM-023 [Middle] JDK dynamic proxy và CGLIB proxy khác nhau thế nào; ảnh hưởng của interface, `final` class/method và self-invocation là gì?

**Kết luận:** JDK proxy triển khai interface; class-based proxy tạo subclass (thường CGLIB trong Spring). Final class/method không thể override để intercept; gọi `this.method()` không đi qua proxy.

**Lập luận:** Caller phải giữ reference proxy do container cấp. Annotation trên implementation/interface và proxy strategy có thể ảnh hưởng pointcut/metadata lookup. Public method là đường dùng phổ biến/an toàn cho proxy advice.

**Pitfall/trade-off:** Inject concrete type có thể fail với JDK proxy. Ép class proxy không sửa self-invocation; tách method sang bean khác hoặc dùng programmatic template phù hợp.

**Mức kỳ vọng:** **Middle:** giải thích `@Transactional` self-call. **Senior:** chẩn đoán proxy type/order/multiple advice và chọn boundary rõ.

### JVM-024 [Senior] Spring AOP dùng proxy khác AspectJ weaving ra sao; pointcut quá rộng, advice ordering và exception swallowing gây rủi ro production nào?

**Kết luận:** Spring AOP proxy chủ yếu intercept method execution đi qua bean proxy; AspectJ weave bytecode có thể bắt constructor/field/call và self-invocation nhưng toolchain/phạm vi mạnh, phức tạp hơn.

**Lập luận:** Pointcut rộng tăng startup/runtime overhead và áp behavior ngoài ý muốn. Nhiều advice transaction/security/retry/log cần order được khai/kiểm thử. Around advice phải `proceed()` đúng số lần và preserve return/exception.

**Pitfall/trade-off:** Nuốt exception có thể làm transaction commit; retry ngoài transaction khác retry trong cùng transaction. Cross-cutting logic che control flow, nên giữ aspect nhỏ và observable.

**Mức kỳ vọng:** **Middle:** hiểu proxy boundary. **Senior:** lý giải advice order/failure semantics và khi weaving đáng giá.

### JVM-025 [Middle] `@Configuration` full mode và lite mode khác nhau thế nào; gọi trực tiếp một `@Bean` method có luôn trả singleton do container quản lý không?

**Kết luận:** Full `@Configuration` thường được enhance để lời gọi giữa `@Bean` methods được intercept và trả bean container; lite mode như `@Component` hoặc `proxyBeanMethods=false` là lời gọi Java bình thường.

**Lập luận:** Với lite mode, method gọi trực tiếp có thể tạo object mới ngoài lifecycle dù bean definition của chính method vẫn do container quản lý. Cách rõ nhất là khai dependency làm parameter của `@Bean` method.

```java
@Bean
OrderService orderService(PaymentClient client) {
  return new OrderService(client);
}
```

**Pitfall/trade-off:** Full proxy không hoạt động với ràng buộc subclass/final tương ứng và có startup overhead nhỏ. Dựa vào self-call làm config khó hiểu.

**Mức kỳ vọng:** **Middle:** dự đoán instance count. **Senior:** chọn lite/full cho AOT/performance và viết config dependency explicit.

### JVM-026 [Senior] `@Conditional`, auto-configuration và thứ tự cấu hình của Spring Boot hoạt động ra sao; cách debug vì sao một bean được/không được tạo là gì?

**Kết luận:** Auto-configuration là config có conditions theo class, bean, property, resource... và thường back off khi user định nghĩa bean; ordering chỉ điều phối evaluation/config, không phải business initialization tùy ý.

**Lập luận:** Kiểm tra Condition Evaluation Report qua debug/Actuator conditions, bean definitions, property source và classpath. `@ConditionalOnMissingBean` phụ thuộc thời điểm definition đã biết; starter nên dùng metadata/ordering chuẩn.

**Pitfall/trade-off:** Tự phỏng đoán từ annotation bỏ sót property precedence hoặc dependency thiếu. Override bean trùng tên có thể bị cấm; không dựa vào accidental scan order.

**Mức kỳ vọng:** **Middle:** đọc report. **Senior:** thiết kế starter backoff/ordering ổn định và debug bằng evidence.

### JVM-027 [Senior] Hãy code review service dùng service locator/ApplicationContext tĩnh: nó che dependency, lifecycle và testability thế nào; lộ trình refactor là gì?

**Kết luận:** Lookup tĩnh biến dependency thành runtime hidden global, cho phép object lấy bất kỳ bean, làm construction/invariant/test và scope lifecycle khó kiểm soát.

**Lập luận:** Inventory lookup, nhóm theo capability, inject interface qua constructor; đưa dynamic selection vào typed factory/strategy registry do container inject. Với legacy static entry point, tạo adapter mỏng tại boundary rồi thu hẹp dần.

**Pitfall/trade-off:** Big-bang refactor rủi ro; không thay global context bằng global singleton tự viết. Provider/ObjectProvider chỉ dùng khi thật sự lazy/optional/multiple.

**Mức kỳ vọng:** **Middle:** nêu hidden coupling. **Senior:** lập incremental migration, xử lý scope/cycle và thêm characterization tests.

## 4. Transaction và tính nhất quán

### JVM-028 [Middle] `@Transactional` được thực thi qua proxy thế nào; vì sao gọi method nội bộ hoặc tạo object bằng `new` có thể làm annotation không hiệu lực?

**Kết luận:** Transaction interceptor trên proxy mở/đóng transaction quanh lời gọi đi qua proxy. Self-invocation và object tự `new` bỏ qua bean proxy nên advice không chạy.

**Lập luận:** Transaction manager bind resource/context với execution thread; method visibility/proxy strategy cũng ảnh hưởng. Tách transactional use case sang bean khác hoặc dùng `TransactionTemplate` cho boundary programmatic.

```java
transactionTemplate.executeWithoutResult(status -> useCase.execute(command));
```

**Pitfall/trade-off:** Kiểm tra transaction chỉ bằng dữ liệu success không bắt lỗi; cần test rollback. Inject self-proxy là workaround dễ làm thiết kế vòng/khó đọc.

**Mức kỳ vọng:** **Middle:** tìm self-call bug. **Senior:** đặt transaction boundary theo use case và xác minh proxy/manager/async thread.

### JVM-029 [Senior] Phân biệt propagation `REQUIRED`, `REQUIRES_NEW`, `NESTED` và `MANDATORY`; connection pool và partial commit bị ảnh hưởng thế nào?

**Kết luận:** REQUIRED join hoặc tạo mới; REQUIRES_NEW suspend outer và mở transaction/resource độc lập; NESTED dùng savepoint trong physical transaction nếu manager hỗ trợ; MANDATORY fail nếu không có transaction.

**Lập luận:** Inner REQUIRED rollback-only có thể làm outer nhận `UnexpectedRollbackException`. REQUIRES_NEW có thể commit dù outer rollback và cần connection khác khi outer đang giữ một connection; concurrent threads dễ cạn pool. NESTED rollback về savepoint nhưng outer commit quyết định cuối.

**Pitfall/trade-off:** Propagation không thay thế distributed consistency. REQUIRES_NEW cho audit có thể mất/commit lệch; savepoint support khác DB/manager.

**Mức kỳ vọng:** **Middle:** dự đoán commit/rollback. **Senior:** phân tích pool sizing, rollback-only và invariant partial commit.

### JVM-030 [Middle] Isolation level ngăn dirty read, non-repeatable read và phantom read ra sao; behavior thực tế phụ thuộc database/MVCC thế nào?

**Kết luận:** Chuẩn SQL tăng từ READ_UNCOMMITTED đến SERIALIZABLE với anomaly được cấm dần, nhưng implementation MVCC/locking và default DB quyết định behavior cụ thể.

**Lập luận:** Dirty read thấy uncommitted; non-repeatable là cùng row đổi; phantom là tập row theo predicate đổi. MVCC snapshot có thể ngăn một số anomaly nhưng vẫn có write skew ở snapshot isolation; serializable có thể abort và cần retry.

**Pitfall/trade-off:** Tên isolation không đủ để chứng minh business invariant. Isolation cao tăng conflict/lock/retry; cần constraint/atomic update/locking đúng case.

**Mức kỳ vọng:** **Middle:** mô tả anomaly. **Senior:** kiểm tra doc DB, dựng concurrent test và bảo vệ invariant cụ thể.

### JVM-031 [Senior] Quy tắc rollback mặc định của Spring là gì; catch exception, checked exception hoặc trả failure object có thể vô tình commit ra sao?

**Kết luận:** Mặc định interceptor rollback với unchecked `RuntimeException` và `Error`, không tự rollback mọi checked exception. Nếu exception bị catch/đổi thành return bình thường, proxy thấy success và commit.

**Lập luận:** Dùng `rollbackFor` khi contract cần, hoặc taxonomy exception phù hợp; tốt hơn để failure vượt transaction boundary. Có thể đánh dấu rollback-only nhưng làm control flow khó thấy và outer có thể nhận unexpected rollback.

**Pitfall/trade-off:** Annotation chỉ có hiệu lực khi đi qua proxy. Rollback DB không hoàn tác email/HTTP/file đã thực hiện.

**Mức kỳ vọng:** **Middle:** biết default và catch bug. **Senior:** thiết kế error/side-effect boundary, test checked/unchecked và propagation.

### JVM-032 [Senior] Tại sao không nên giữ database transaction trong lúc gọi HTTP/message broker; hãy thiết kế timeout, outbox, idempotency và compensation cho workflow liên dịch vụ.

**Kết luận:** External call kéo dài/không xác định làm giữ connection/lock, tăng deadlock và không thể atomic với DB local. Commit DB và publish event qua transactional outbox, consumer idempotent.

**Lập luận:** Cùng transaction ghi business state + outbox; relay retry publish; consumer dedupe bằng stable event/operation ID và unique constraint. Workflow dài dùng saga/state machine với retry deadline và compensation business, không giả vờ distributed rollback.

**Pitfall/trade-off:** Outbox cho at-least-once nên duplicate/order vẫn phải xử lý. Compensation không luôn đảo ngược hoàn hảo. Timeout mọi hop và tránh retry nhiều tầng.

**Mức kỳ vọng:** **Middle:** không gọi HTTP trong lock dài. **Senior:** thiết kế atomic boundary, idempotency key, ordering/replay và failure recovery.

### JVM-033 [Senior] `@Transactional(readOnly = true)` là hint hay guarantee; nó ảnh hưởng flush, driver/database optimization và correctness thế nào?

**Kết luận:** Chủ yếu là hint truyền qua transaction manager/provider; không phải security guarantee phổ quát rằng mọi write bị cấm.

**Lập luận:** Tùy stack, nó có thể set connection read-only, chọn routing replica hoặc điều chỉnh Hibernate flush behavior. Database/driver có thể enforce khác nhau. Managed entity vẫn có thể mutate trong memory; việc flush hay reject phải kiểm chứng.

**Pitfall/trade-off:** Dựa vào readOnly để bảo vệ dữ liệu là sai; dùng DB permission/architecture. Replica routing gặp read-after-write lag; read-only transaction dài vẫn giữ snapshot/resource.

**Mức kỳ vọng:** **Middle:** coi là optimization hint. **Senior:** biết behavior stack cụ thể, test flush/routing và giữ correctness độc lập hint.

## 5. Spring MVC, WebFlux và API

### JVM-034 [Middle] Request đi qua filter, security filter chain, `DispatcherServlet`, interceptor, argument resolver, controller và exception handler theo thứ tự nào?

**Kết luận:** Servlet filter chạy ngoài MVC; Spring Security là một filter chain trong lớp này. Sau đó `DispatcherServlet` chọn handler, interceptor `preHandle`, resolver bind arguments, controller chạy; resolver/exception handler xử lý lỗi; post/after callbacks rồi filter unwind.

**Lập luận:** `postHandle` chỉ khi handler thành công trước render; `afterCompletion` dùng cleanup sau hoàn tất. Error có thể bị xử lý ở filter hoặc MVC tùy phát sinh ở đâu, nên `@ControllerAdvice` không bắt mọi filter exception.

**Pitfall/trade-off:** Đọc body ở filter có thể consume stream nếu không wrap/cache đúng. Ordering security/CORS/tracing ảnh hưởng behavior.

**Mức kỳ vọng:** **Middle:** vẽ pipeline chính. **Senior:** đặt auth/log/error/context đúng layer và xử lý async dispatch.

### JVM-035 [Senior] Thiết kế error response cho REST API thế nào để ổn định, traceable và không leak nội bộ; mapping validation/domain/infrastructure error nên đặt ở đâu?

**Kết luận:** Public response có stable machine code/type, status, safe message, field violations và trace/correlation ID; stack/SQL/internal host chỉ ở protected logs/traces.

**Lập luận:** DTO validation map 400/422 theo contract; not-found/conflict/domain rule map status ổn định; auth 401/403 đúng nghĩa; unknown dependency failure thường 5xx. Central `@ControllerAdvice`/ProblemDetail adapter giữ mapping nhất quán, domain không phụ thuộc HTTP.

**Pitfall/trade-off:** Trả exception class/message làm API không ổn định/leak. Log cùng lỗi mọi tầng gây noise; correlation ID không phải secret nhưng cần tránh user-controlled spoof.

**Mức kỳ vọng:** **Middle:** mapping/validation rõ. **Senior:** version error schema, observability và threat model/retry semantics.

### JVM-036 [Middle] Bean Validation hoạt động ở request DTO và method boundary thế nào; vì sao không nên dùng JPA entity trực tiếp làm API contract?

**Kết luận:** `@Valid` cascade graph trên request binding; method validation qua proxy kiểm tra parameter/return khi được enable. API DTO tách transport schema khỏi persistence model/lifecycle.

**Lập luận:** Validation group/cross-field custom constraint dùng khi cần, nhưng domain invariant vẫn phải bảo vệ trong domain. Entity trực tiếp dễ over-posting, lazy serialization, recursion, leak field và migration schema ngoài ý muốn.

**Pitfall/trade-off:** `@NotNull` không tự chạy nếu thiếu `@Valid`/method interceptor đúng boundary. Mapping DTO có code thêm nhưng tạo compatibility/security boundary.

**Mức kỳ vọng:** **Middle:** dùng DTO và xử lý violation. **Senior:** phân tầng syntactic/domain validation, group ít lạm dụng và chống mass assignment.

### JVM-037 [Senior] Spring MVC thread-per-request và WebFlux event loop khác nhau thế nào; blocking JDBC/call trong reactive chain phá throughput ra sao?

**Kết luận:** MVC thường cho request chiếm thread trong lúc blocking; WebFlux multiplex nhiều request trên ít event-loop thread, nên một blocking call giữ event loop và đình trệ nhiều request.

**Lập luận:** Reactive chỉ có lợi end-to-end nonblocking hoặc concurrency rất cao. Nếu phải dùng blocking library, isolate vào bounded scheduler thích hợp nhưng vẫn capacity-plan; JDBC không tự nonblocking chỉ vì bọc `Mono`.

**Pitfall/trade-off:** WebFlux tăng complexity/context debugging và không làm CPU task nhanh. MVC + virtual threads có thể đơn giản hơn cho blocking stack, nhưng downstream vẫn cần bound.

**Mức kỳ vọng:** **Middle:** không `block` trên event loop. **Senior:** chọn stack theo dependency/workload và đo queue/latency/backpressure.

### JVM-038 [Senior] Backpressure, cancellation và context propagation trong Reactor hoạt động thế nào; lỗi phổ biến với `subscribe()`, `block()` và MDC là gì?

**Kết luận:** Subscriber phát demand (`request(n)`), operator truyền/điều tiết; cancellation đi upstream cooperative. Reactor Context đi cùng subscription, khác `ThreadLocal` vì execution đổi thread.

**Lập luận:** Framework thường là subscriber cuối; tự `subscribe()` trong service tạo detached work, mất error/cancel/transaction composition. `block()` trên nonblocking thread có thể deadlock/starvation. MDC cần bridge/lifter/context-aware integration, không set một lần theo thread.

**Pitfall/trade-off:** Backpressure không thể ép API push ngoài hệ thống nếu adapter không buffer/drop/rate-limit. Unbounded `flatMap` vẫn overload downstream.

**Mức kỳ vọng:** **Middle:** return publisher thay tự subscribe. **Senior:** thiết kế concurrency/prefetch/buffer policy, deadline/cancel và context propagation có test.

## 6. Security, configuration và testing Spring

### JVM-039 [Middle] Authentication và authorization khác nhau thế nào; Spring Security lưu `SecurityContext` ở đâu và cần chú ý gì với async/reactive execution?

**Kết luận:** Authentication xác định principal; authorization quyết định principal được phép làm gì. Servlet stack thường gắn context với request và thread-local strategy; reactive dùng Reactor Context.

**Lập luận:** Qua executor/`@Async`, ThreadLocal không tự truyền an toàn; dùng delegating security-context executor hoặc truyền identity/context theo cơ chế framework. Context phải được clear ở request end để tránh leak giữa thread pool tasks.

**Pitfall/trade-off:** Copy context quá lâu tạo confused-deputy/stale privilege. Không tin role/tenant ID từ request nếu chưa bind với authenticated principal.

**Mức kỳ vọng:** **Middle:** phân biệt 401/403 và authn/authz. **Senior:** bảo toàn/giới hạn context qua async, tenant và method authorization.

### JVM-040 [Senior] CSRF, CORS, session fixation và cookie flags bảo vệ các threat khác nhau thế nào; khi nào API bearer-token có thể tắt CSRF an toàn?

**Kết luận:** CSRF chống trình duyệt tự gửi credential; CORS kiểm soát JS đọc/gửi cross-origin, không phải auth; session fixation đổi session ID sau login; Secure/HttpOnly/SameSite giảm các đường cookie attack.

**Lập luận:** API stateless chỉ nhận bearer trong `Authorization` mà browser không tự đính kèm thường không cần CSRF token. Nếu credential nằm cookie, basic/client cert hoặc cơ chế tự gửi, CSRF vẫn liên quan. XSS có thể đánh cắp token/ra lệnh dù CORS đúng.

**Pitfall/trade-off:** `Access-Control-Allow-Origin: *` với credentials không hợp lệ/nguy hiểm; tắt CSRF chỉ vì “REST” là thiếu threat model.

**Mức kỳ vọng:** **Middle:** cấu hình CORS/cookie đúng. **Senior:** threat-model credential transport, preflight, same-site flows và defense-in-depth.

### JVM-041 [Senior] Thiết kế JWT validation cần kiểm tra signature, issuer, audience, expiry, algorithm và key rotation thế nào; revoke/logout là trade-off gì?

**Kết luận:** Chỉ chấp nhận algorithm allowlist, verify signature bằng key tin cậy, validate issuer/audience/time claims và token type; resolve `kid` qua cache/JWKS có refresh/rate limit và rotation overlap.

**Lập luận:** Clock skew nhỏ có chủ đích; access token ngắn hạn giảm window. Logout/revoke tức thời cần state như denylist/session/introspection, làm mất tính hoàn toàn stateless; refresh token cần rotation/reuse detection.

**Pitfall/trade-off:** Không tin algorithm/header/key URL tùy token; không log token. JWT được ký không đồng nghĩa encrypted; claim nhạy cảm vẫn đọc được.

**Mức kỳ vọng:** **Middle:** validate signature/exp. **Senior:** thiết kế trust/key failure/rotation/revocation và tenant/audience isolation.

### JVM-042 [Middle] Externalized configuration và profile trong Spring Boot nên được tổ chức thế nào; precedence, secret và type-safe `@ConfigurationProperties` cần lưu ý gì?

**Kết luận:** Bind config theo namespace vào validated typed object; default an toàn trong code/config, override theo môi trường qua nguồn triển khai. Secret đi qua secret manager/file/identity, không commit.

**Lập luận:** Property source có precedence; cần dùng Actuator/env report cẩn trọng để biết value đến từ đâu và redact. Profile chỉ nhóm cấu hình môi trường/use case, tránh hàng chục tổ hợp logic khó dự đoán.

**Pitfall/trade-off:** `@Value` rải rác mất validation/discoverability. Environment variable string dễ sai type/name. Không log full config hoặc secret ở startup.

**Mức kỳ vọng:** **Middle:** dùng `@ConfigurationProperties` + validation. **Senior:** quản lý schema/evolution, precedence audit, secret rotation và immutable config.

### JVM-043 [Senior] So sánh unit test thuần, slice test và `@SpringBootTest`; context caching, test isolation và Testcontainers ảnh hưởng tốc độ/độ tin cậy ra sao?

**Kết luận:** Unit test không context cho logic; slice chỉ nạp tầng liên quan; full context xác nhận wiring/runtime gần thật. Testcontainers cho dependency thật, đổi lại startup/resource cost.

**Lập luận:** Spring cache context khi configuration key giống nhau; nhiều mock/profile/dynamic property khác nhau phá reuse. Reset dữ liệu bằng transaction/truncate/schema riêng; container có thể reuse theo suite nhưng test vẫn độc lập.

**Pitfall/trade-off:** `@DirtiesContext` tràn lan làm suite chậm. H2 không mô phỏng đầy đủ dialect/locking của production. Full-context test cho mọi case tạo feedback chậm.

**Mức kỳ vọng:** **Middle:** chọn đúng tầng test. **Senior:** tối ưu context topology/parallel isolation và kiểm thử DB/message contract thật.

### JVM-044 [Senior] Hãy code review test dùng `@MockBean` cho hầu hết dependency: nó có thể bỏ sót wiring, proxy, serialization và transaction bug thế nào; test pyramid nên cân bằng ra sao?

**Kết luận:** MockBean thay definition trong context nên test có vẻ “Spring” nhưng phần tích hợp quan trọng bị loại; mock interaction dễ khóa implementation.

**Lập luận:** Giữ unit test thuần cho branching; slice test serialization/validation/security; integration full context + real DB/broker cho transaction/query/wiring; contract/end-to-end ít hơn cho critical flow. Mock external port, không mock repository khi muốn test JPA.

**Pitfall/trade-off:** Xóa toàn bộ mock làm suite chậm/flaky; mục tiêu là mock theo boundary/risk. MockBean variants làm context cache fragmentation.

**Mức kỳ vọng:** **Middle:** nhận ra false confidence. **Senior:** lập portfolio theo failure mode, feedback budget và production parity.

## 7. JPA/Hibernate và persistence

### JVM-045 [Middle] Entity lifecycle/transitions (`transient`, `managed`, `detached`, `removed`) và dirty checking hoạt động thế nào trong persistence context?

**Kết luận:** Transient chưa được context quản lý; managed được identity map/dirty checking; detached từng managed nhưng context đóng/clear; removed được đánh dấu xóa khi flush/commit.

**Lập luận:** `persist` làm new entity managed; query/find trả managed; `detach/clear/close` tách; `merge` copy state vào managed instance và trả instance đó, không reattach chính object argument. Flush đồng bộ thay đổi với DB trước/ở commit tùy mode.

**Pitfall/trade-off:** Giữ context quá lâu phình memory/stale state. Gọi save không phải lúc nào lập tức SQL; exception có thể xuất hiện lúc flush.

**Mức kỳ vọng:** **Middle:** dự đoán SQL/dirty checking. **Senior:** đặt persistence-context boundary, flush point và tránh detached merge overwrite.

### JVM-046 [Senior] N+1 query xuất hiện với lazy/eager association ra sao; phát hiện và xử lý bằng fetch join, entity graph, batch fetch hoặc projection thế nào?

**Kết luận:** Một query lấy N parent rồi truy cập association phát thêm N query; EAGER không đảm bảo một query và còn có thể làm fetch ngoài ý muốn.

**Lập luận:** Phát hiện bằng SQL/query count/APM integration test. Fetch join/entity graph cho use case cần graph; batch fetch gom nhiều proxy; projection chỉ lấy trường cần. Chọn plan theo endpoint, không đổi mọi relation sang eager.

```java
@EntityGraph(attributePaths = "orders")
Optional<Customer> findDetailedById(Long id);
```

**Pitfall/trade-off:** Fetch join nhiều to-many tạo Cartesian explosion/duplicate và khó paginate. Batch giảm N+1 thành ít query chứ không luôn tối ưu; OSIV có thể che lỗi và query trong serialization.

**Mức kỳ vọng:** **Middle:** nhận diện từ log. **Senior:** định lượng rows/queries, thiết kế use-case query và test query budget.

### JVM-047 [Middle] `LAZY` và `EAGER` là contract gì, không phải query plan như thế nào; `LazyInitializationException` phản ánh boundary thiết kế nào?

**Kết luận:** EAGER yêu cầu association sẵn trước khi entity usable theo contract; LAZY cho phép trì hoãn. Provider vẫn chọn join hay query phụ, nên fetch type không phải câu lệnh SQL plan.

**Lập luận:** Lazy proxy/collection cần open persistence context để initialize. Exception cho thấy code truy cập graph ngoài data-access/use-case boundary mà chưa fetch/mapping đủ; map DTO trong transaction hoặc query projection.

**Pitfall/trade-off:** Bật OSIV hoặc đổi EAGER chữa symptom nhưng tạo hidden query/connection lifetime. Không serialize entity graph trực tiếp.

**Mức kỳ vọng:** **Middle:** fix bằng explicit fetch/DTO. **Senior:** định nghĩa aggregate/query boundary và tránh over-fetch.

### JVM-048 [Senior] Optimistic locking với `@Version` và pessimistic locking khác nhau về contention, retry và deadlock; chọn theo invariant/workload thế nào?

**Kết luận:** Optimistic update kiểm tra version và fail khi conflict, hợp read-heavy/conflict thấp; pessimistic giữ DB lock, hợp critical section ngắn/conflict cao nhưng tăng wait/deadlock.

**Lập luận:** Optimistic failure cần retry toàn use case với dữ liệu đọc lại, bounded/backoff và chỉ khi side effect idempotent. Pessimistic cần lock order, timeout và transaction ngắn; DB isolation/lock mode phải kiểm tra.

**Pitfall/trade-off:** Retry chỉ câu UPDATE sau conflict có thể vi phạm decision dựa state cũ. Lock row không bảo vệ predicate/range invariant nếu DB không khóa tương ứng.

**Mức kỳ vọng:** **Middle:** hiểu version conflict. **Senior:** chọn theo probability/cost conflict và chứng minh invariant bằng concurrent test.

### JVM-049 [Senior] Hãy thiết kế `equals()`/`hashCode()` cho JPA entity khi ID được sinh sau persist và entity có proxy; business key và collection membership gây pitfall gì?

**Kết luận:** Equality phải ổn định suốt thời gian entity nằm trong hash collection và hoạt động với proxy. Immutable natural/business key duy nhất là lựa chọn tốt nếu thật sự tồn tại; generated ID đòi strategy cẩn trọng.

**Lập luận:** Hai entity transient với `id=null` không được coi equal chỉ vì cùng null. Sau persist, hash dựa ID đổi sẽ làm mất membership. Có thể equality theo non-null ID và hash class ổn định/constant theo pattern provider khuyến nghị, đồng thời xử lý effective class/proxy nhất quán.

**Pitfall/trade-off:** `getClass()` thuần có thể khác proxy; `instanceof` có thể phá symmetry trong inheritance. Business key mutable cũng hỏng hash và có thể trigger lazy load.

**Mức kỳ vọng:** **Middle:** tránh Lombok auto-equality toàn field. **Senior:** document identity lifecycle, proxy/inheritance và test transient-managed-detached/set behavior.

### JVM-050 [Senior] JDBC batching của Hibernate bị ảnh hưởng bởi ID generation, flush/clear, ordering và relationship thế nào; cách import hàng triệu dòng mà không phình persistence context là gì?

**Kết luận:** Bật driver/Hibernate batch và flush/clear theo chunk; sequence/pooled ID thường batch insert tốt hơn IDENTITY vì cần ID ngay có thể buộc insert từng dòng.

**Lập luận:** `order_inserts/order_updates` gom statement tương tự; batch size cân bằng round trip/memory. Import lớn dùng stateless session/JDBC batch hoặc chunk transaction nếu domain hook không cần, đồng thời kiểm soát cascade và logging.

```java
for (int i = 0; i < rows.size(); i++) {
  entityManager.persist(toEntity(rows.get(i)));
  if ((i + 1) % batchSize == 0) { entityManager.flush(); entityManager.clear(); }
}
```

**Pitfall/trade-off:** `saveAll` không bảo đảm batch nếu config/ID/SQL shape khác. Một transaction triệu dòng giữ undo/lock và recovery đắt. Clear làm entity detached, phải quản lý reference.

**Mức kỳ vọng:** **Middle:** flush/clear chunk và xem SQL. **Senior:** benchmark driver/network/commit size, ID strategy và failure-resume/idempotency.

### JVM-051 [Senior] Cascade và `orphanRemoval` khác nhau thế nào; cấu hình sai trên aggregate lớn hoặc many-to-many có thể xóa dữ liệu ngoài ý muốn ra sao?

**Kết luận:** Cascade truyền operation entity (`PERSIST`, `REMOVE`...); orphanRemoval xóa child khi bị tách khỏi quan hệ sở hữu. Chỉ dùng theo aggregate ownership thật.

**Lập luận:** Parent sở hữu lifecycle child one-to-many thường phù hợp cascade persist + orphan. Many-to-many là hai aggregate chia sẻ; cascade REMOVE có thể xóa entity phía kia thay vì chỉ join row. Hai phía helper method phải giữ association đồng bộ.

**Pitfall/trade-off:** Replace collection/detached merge có thể đánh dấu hàng loạt orphan; cascade graph lớn tạo SQL storm. DB cascade và ORM cascade cần phối hợp để không double/confusing state.

**Mức kỳ vọng:** **Middle:** phân biệt cascade/orphan. **Senior:** mô hình hóa ownership, review delete SQL và bảo vệ bulk/merge scenario.

## 8. Build, đóng gói và deploy

### JVM-052 [Middle] Maven/Gradle dependency scope/configuration, transitive dependency và lock/convergence ảnh hưởng build reproducibility thế nào?

**Kết luận:** Scope/configuration quyết định compile/runtime/test/API exposure; transitive graph có thể chọn version khác theo mediation. Reproducible build cần pin dependency/plugin/toolchain, repository tin cậy và convergence/lock policy.

**Lập luận:** Maven `dependencyManagement`/BOM quản version; Gradle constraints/platform/lockfile kiểm soát resolution. Wrapper khóa build tool; checksum/verification và immutable artifact tránh supply-chain drift.

**Pitfall/trade-off:** Dynamic range/SNAPSHOT làm cùng commit ra artifact khác. Lock tuyệt đối giảm drift nhưng cần quy trình update/security patch; exclusion phải kiểm chứng runtime.

**Mức kỳ vọng:** **Middle:** đọc dependency tree/scope. **Senior:** quản BOM/lock/SBOM, plugin/toolchain và CI hermeticity.

### JVM-053 [Senior] Fat JAR, layered container image, CDS và native image khác nhau về startup, memory, build time, reflection và khả năng debug ra sao?

**Kết luận:** Fat JAR đơn giản/portable JVM nhưng image layer có thể invalidate lớn; layered image tách dependency/app để cache. CDS chia sẻ/preload class metadata. Native image AOT cho startup/RSS tốt ở nhiều case nhưng build chậm/closed-world và dynamic feature khó hơn.

**Lập luận:** Native image cần metadata cho reflection/proxy/resource/JNI và profile/test đúng binary; peak throughput/debug/JFR capability khác JVM tùy stack/version. CDS giữ JVM semantics/tooling gần quen thuộc.

**Pitfall/trade-off:** Native không mặc định ít memory hoặc nhanh hơn mọi workload; build/profile-guided complexity. Layer sai làm cache vô ích; distroless giảm shell nhưng incident workflow cần tooling bên ngoài.

**Mức kỳ vọng:** **Middle:** hiểu packaging/cache. **Senior:** benchmark startup/RSS/throughput, audit framework compatibility và operability/supply chain.

### JVM-054 [Senior] JVM trong container cần cấu hình heap, CPU, direct memory và thread thế nào theo cgroup limit; vì sao chỉ đặt `-Xmx` vẫn có thể bị OOMKilled?

**Kết luận:** Cgroup giới hạn toàn process: heap + metaspace + code cache + direct/native + thread stacks + agents/libs/page cache liên quan. `-Xmx` sát limit không chừa headroom nên kernel kill trước Java OOME.

**Lập luận:** Đặt memory budget từng vùng/MaxRAMPercentage theo workload, theo dõi RSS/working set và NMT; giới hạn direct memory/thread/concurrency khi cần. CPU quota ảnh hưởng GC/compiler/common-pool ergonomics, phải kiểm tra JDK container awareness/version.

**Pitfall/trade-off:** Giảm stack mù quáng gây overflow; đặt heap quá thấp tăng GC. Kubernetes request khác limit; OOMKilled không tạo heap dump đáng tin nếu kernel giết.

**Mức kỳ vọng:** **Middle:** chừa non-heap headroom. **Senior:** capacity model theo cgroup, load-test throttle/OOM và cấu hình observability/dump an toàn.

### JVM-055 [Senior] Thiết kế graceful shutdown và zero-downtime deploy cho Spring service thế nào: readiness, draining, shutdown timeout, in-flight request, consumer offset và migration tương thích cần phối hợp ra sao?

**Kết luận:** Đánh readiness false/ngừng nhận traffic trước, chờ load balancer propagate và drain in-flight trong deadline; sau đó đóng consumer/executor/resource theo thứ tự, cuối cùng force stop có metric.

**Lập luận:** HTTP request có deadline/idempotency; consumer pause, hoàn tất hoặc abandon an toàn rồi commit offset đúng semantics. Startup readiness chỉ true sau dependency/migration cần thiết. Database/message schema deploy theo expand-migrate-contract để old/new version cùng chạy.

**Pitfall/trade-off:** Liveness không nên fail vì dependency tạm thời gây restart storm. Grace period ngắn làm request/offset lặp; quá dài làm rollout kẹt. `preStop`/signal và Spring shutdown timeout phải khớp orchestrator.

**Mức kỳ vọng:** **Middle:** cấu hình graceful shutdown/readiness. **Senior:** thiết kế timeline có budget, idempotent recovery, backward-compatible migration và game-day test.

## 9. Câu hỏi kinh điển bổ sung — Basic đến Senior

### JVM-056 [Basic · ⭐ Rất thường gặp] JDK, JRE và JVM khác nhau ở vai trò/công cụ nào; một ứng dụng Java cần những thành phần gì ở build time và runtime?

**Kết luận:** JVM thực thi bytecode và cung cấp runtime services; JRE là JVM cộng standard runtime libraries/resources; JDK bao gồm runtime cùng compiler và công cụ phát triển/diagnostic.

**Cơ chế:** Build cần JDK như `javac`, linker/build tooling; chạy cần runtime tương thích, có thể là JDK đầy đủ hoặc custom image tạo bằng `jlink`. JVM implementation phụ thuộc OS/CPU nhưng class file tuân specification chung.

**Pitfall / follow-up Senior:** “JRE” là khái niệm hữu ích nhưng cách đóng gói distribution hiện đại khác thời JRE cài riêng. Phải pin vendor/version/architecture, target class-file version và kiểm thử custom image có đủ module/diagnostic tool.

### JVM-057 [Basic · ⭐ Rất thường gặp] Khi nào một object đủ điều kiện được garbage collector thu hồi; reference cycle có ngăn GC không và `System.gc()` có bảo đảm collection ngay không?

**Kết luận:** Object đủ điều kiện khi không còn reachable theo strong path từ GC roots; cycle tự tham chiếu vẫn thu được nếu cả cycle unreachable. `System.gc()` chỉ là request/hint và có thể bị bỏ qua hoặc trì hoãn.

**Cơ chế:** Collector tracing bắt đầu từ thread stacks, static fields, JNI references và roots runtime rồi đánh dấu graph reachable; nó không dùng reference counting thuần. Việc “eligible” không xác định chính xác lúc memory được reclaim.

**Pitfall / follow-up Senior:** Không dùng `System.gc()` như lifecycle/pressure control và không dựa finalizer. Senior nên phân biệt unreachable với retained-by-cache/ThreadLocal/classloader và dùng path-to-GC-root để chứng minh leak.

### JVM-058 [Basic · ⭐ Rất thường gặp] `@Component`, `@Service`, `@Repository` và `@Controller` khác nhau thế nào ngoài ý nghĩa đặt tên; annotation nào có thêm semantics framework đáng chú ý?

**Kết luận:** Cả bốn là stereotype dựa trên `@Component` để component scan đăng bean; Service chủ yếu diễn đạt application/service role, Controller tham gia MVC handler discovery, Repository đánh dấu persistence adapter.

**Cơ chế:** `@Controller` được MVC infrastructure tìm cùng mapping; `@Repository` còn là điểm áp persistence-exception translation khi post-processor tương ứng hoạt động. Custom stereotype có thể meta-annotate Component và alias attribute.

**Pitfall / follow-up Senior:** Annotation không tự bảo đảm architecture/layer rule hay transaction. Exception translation phụ thuộc bean/proxy/config; dùng stereotype đúng nghĩa giúp scan, test slice và static architecture checks đáng tin hơn.

### JVM-059 [Basic · ⭐ Rất thường gặp] Component scanning tìm và đăng ký bean ra sao; package đặt sai hoặc có hai bean cùng type gây lỗi injection nào?

**Kết luận:** Spring scan base packages, đọc candidate stereotype/configuration và đăng BeanDefinition trước khi instantiate. Không scan tới package tạo `NoSuchBeanDefinitionException`; nhiều candidate cho dependency đơn tạo `NoUniqueBeanDefinitionException` nếu không phân giải được.

**Cơ chế:** `@SpringBootApplication` ngầm component-scan từ package của application class xuống subpackage; có thể dùng explicit `@ComponentScan`/`@Import`. Bean name conflict là vấn đề khác ambiguity theo type và tùy policy có thể fail lúc registration.

**Pitfall / follow-up Senior:** Scan quá rộng tăng startup và vô tình kéo config/test component; scan quá hẹp tạo wiring chỉ lỗi theo môi trường. Module lớn nên dùng explicit configuration/import boundary thay vì dựa package accident.

### JVM-060 [Basic · ⭐ Rất thường gặp] `@Controller`, `@RestController` và `@ResponseBody` khác nhau thế nào trong Spring MVC?

**Kết luận:** Controller mặc định trả logical view/model; `@ResponseBody` trên method ghi return value vào response qua message converter; RestController tương đương Controller + ResponseBody mặc định cho mọi handler.

**Cơ chế:** Handler return được `HandlerMethodReturnValueHandler` xử lý; response body được content negotiation và `HttpMessageConverter` serialize, không phải tên view. Có thể trả `ResponseEntity` để điều khiển status/header/body.

**Pitfall / follow-up Senior:** Serialize entity trực tiếp dễ lazy query, recursion và leak field. REST contract nên dùng DTO, stable error schema và explicit content/status semantics.

### JVM-061 [Basic · ⭐ Rất thường gặp] HTTP method GET, POST, PUT, PATCH và DELETE khác nhau về safety/idempotency thế nào; vì sao retry policy phải dựa trên semantics thực tế?

**Kết luận:** GET là safe và idempotent; PUT/DELETE được định nghĩa idempotent về intended effect; POST thường không; PATCH phụ thuộc patch semantics. Idempotent không có nghĩa response/log/timestamp giống hệt hay operation không có side effect phụ.

**Cơ chế:** Retry sau timeout xảy ra khi client không biết server đã commit; method semantics, idempotency key và conditional request quyết định có lặp an toàn. DELETE lặp có thể trả 404 nhưng resource state vẫn như sau lần đầu.

**Pitfall / follow-up Senior:** Không retry write chỉ dựa tên verb nếu implementation tăng counter/gửi email mỗi lần. POST payment cần key/dedup/result replay; retry phải bounded, có timeout/backoff và chỉ với lỗi transient.

### JVM-062 [Basic · ⭐ Rất thường gặp] JPA, Hibernate và Spring Data JPA là gì, mỗi lớp chịu trách nhiệm nào và repository abstraction có làm biến mất persistence concern không?

**Kết luận:** JPA/Jakarta Persistence là specification API/semantics ORM; Hibernate là provider triển khai và có extension; Spring Data JPA tạo repository/query integration trên JPA/Spring.

**Cơ chế:** EntityManager/persistence context, mapping, lifecycle và query language đến từ JPA; Hibernate quyết định SQL/fetch/dirty-check implementation; Spring Data sinh proxy repository, derived query và paging. Database/driver vẫn quyết định plan, lock và constraint.

**Pitfall / follow-up Senior:** Repository không xóa N+1, transaction boundary, indexing hay flush semantics. Generic repository bọc lại Spring Data có thể che projection/fetch/query capability mà không tạo domain abstraction thật.

### JVM-063 [Middle · Thường gặp] Thread Context ClassLoader và `ServiceLoader` giúp framework/plugin tìm implementation ra sao; điều gì hỏng khi task chạy trong container hoặc executor với context loader sai?

**Kết luận:** TCCL cho code framework ở parent loader nhìn provider/resource của application/child loader; ServiceLoader có thể dùng loader được chỉ định hoặc context loader để tìm `META-INF/services`/module provider.

**Cơ chế:** Container đặt context loader khi chuyển control vào ứng dụng. Task chạy pool được tạo ở context khác có thể không thấy provider, thấy version sai hoặc giữ loader cũ qua redeploy; code cần capture/set/restore đúng loader hoặc truyền loader explicit.

**Pitfall / follow-up Senior:** Set TCCL mà không restore trong `finally` gây cross-tenant/plugin leak; thread sống lâu giữ loader và metaspace. JPMS service `uses/provides` và native/AOT discovery cần cấu hình khác classpath scan.

### JVM-064 [Middle · ⭐ Rất thường gặp] Spring chọn dependency khi có nhiều bean cùng interface theo type, tên, `@Primary` và `@Qualifier` ra sao; inject collection khác inject một bean thế nào?

**Kết luận:** Spring lọc candidate theo required type và qualifier; với một injection point, một Primary có thể phá tie, còn tên parameter/field có thể là fallback theo điều kiện metadata/config. Không còn đúng một candidate thì injection fail.

**Cơ chế:** `@Qualifier` thể hiện semantic tag/name cụ thể hơn Primary; inject `List<Port>` nhận tất cả candidate phù hợp và có thể sắp bằng `@Order`/Ordered, thay vì chọn một winner. Optional/ObjectProvider thay đổi absence/lazy semantics.

**Pitfall / follow-up Senior:** Dựa vào parameter name ngầm dễ vỡ khi refactor/compiler metadata đổi; dùng qualifier có domain meaning. Primary tràn lan che configuration ambiguity, còn collection injection cần kiểm soát order và duplicate side effect.

### JVM-065 [Middle · ⭐ Rất thường gặp] Prototype/request-scoped bean được inject vào singleton có lifetime thực tế thế nào; khi nào cần scoped proxy hoặc `ObjectProvider`?

**Kết luận:** Dependency prototype được resolve một lần lúc singleton được tạo nên singleton giữ chính instance đó; request bean cần proxy/provider để resolution diễn ra trong request hiện tại.

**Cơ chế:** Scoped proxy là object ổn định được inject vào singleton nhưng delegate mỗi call tới target của active scope; ObjectProvider cho lookup explicit theo lần cần. Container không tự quản destruction đầy đủ của prototype sau khi trao cho caller.

**Pitfall / follow-up Senior:** Scoped proxy dùng ngoài active request sẽ fail và che dependency context-sensitive; provider/service locator lạm dụng làm coupling ẩn. Tốt hơn truyền request data explicit khi domain/service không thật sự cần request-scoped object.

### JVM-066 [Middle · ⭐ Rất thường gặp] Servlet Filter, Spring MVC HandlerInterceptor và Spring AOP phù hợp ba loại cross-cutting concern nào; boundary và khả năng thấy request/method khác nhau ra sao?

**Kết luận:** Filter bao quanh servlet request/response thô; interceptor hoạt động quanh MVC handler đã mapping; AOP bao quanh method call đi qua Spring proxy ở bất kỳ layer bean phù hợp.

**Cơ chế:** Filter hợp CORS/security header/body wrapper/tracing sớm; interceptor hợp handler metadata, locale, MVC auth/audit; AOP hợp transaction, method metric/policy không phụ thuộc HTTP. ControllerAdvice xử lý MVC exception nhưng không bắt lỗi xảy ra trước DispatcherServlet.

**Pitfall / follow-up Senior:** Đặt cùng concern ở cả ba tạo double logging/order khó đoán. AOP bỏ qua self-invocation/final method, interceptor không thấy non-MVC endpoint, filter đọc body phải wrap stream và giới hạn dữ liệu.

### JVM-067 [Middle · ⭐ Rất thường gặp] Transaction context của Spring có tự truyền qua `@Async`, executor hoặc thread mới không; đặt async boundary sai gây partial commit hoặc query ngoài transaction thế nào?

**Kết luận:** Transaction resource thường thread-bound và không tự truyền sang thread async. Outer method có thể commit/rollback độc lập trong khi task chạy không transaction hoặc mở transaction mới nếu lời gọi đi qua proxy phù hợp.

**Cơ chế:** `@Async` trả control trước completion; lazy entity/context không còn hợp lệ, exception async không rollback outer và side effect có thể chạy dù outer rollback. Commit state rồi phát việc qua transactional outbox/event bền vững, hoặc đặt transaction boundary riêng trong worker.

**Pitfall / follow-up Senior:** Không truyền EntityManager/connection/transaction object qua thread. Context propagation chỉ nên mang metadata an toàn, không biến local ACID thành distributed transaction; cần idempotency, deadline và failure observation.

**Kết luận:** PathVariable lấy segment đã route, RequestParam lấy query/form parameter, RequestBody nhờ message converter decode body theo content type thành object; `@Valid`/`@Validated` kiểm tra constraint sau khi bind.

**Cơ chế:** Conversion/type mismatch hoặc body malformed/unsupported media type xảy ra trước domain validation và thường map 400/415; validation tạo violation theo field/object. Argument resolver, converter và exception resolver tạo pipeline này.

**Pitfall / follow-up Senior:** DTO parse thành công không có nghĩa domain invariant hợp lệ. Cần giới hạn body/depth, không bind entity trực tiếp, phân biệt stable error code cho malformed với violation và không echo raw sensitive input.

### JVM-069 [Middle · Thường gặp] PUT và PATCH nên được thiết kế thế nào về replace/partial update, idempotency, validation và lost-update protection bằng ETag/version?

**Kết luận:** PUT thường thay toàn representation tại URI và idempotent; PATCH mô tả partial change, có thể idempotent hoặc không tùy operation format. Cả hai cần validation trên resulting state và optimistic precondition.

### JVM-070 [Middle · ⭐ Rất thường gặp] Trong quan hệ JPA hai chiều, owning side và `mappedBy` quyết định SQL/update foreign key thế nào; vì sao phải đồng bộ cả hai phía trong memory?

**Kết luận:** Owning side chứa mapping foreign key/join table và thay đổi ở phía đó quyết định association SQL; `mappedBy` đánh dấu inverse side chỉ phản chiếu quan hệ.

### JVM-071 [Senior · Thường gặp] JVM báo `OutOfMemoryError: unable to create native thread` dù heap còn trống: hãy điều tra thread count, `-Xss`, OS/cgroup PID-memory limit và nguồn tạo thread thế nào?

### JVM-072 [Senior · Thường gặp] `@TransactionalEventListener` ở các phase khác nhau có guarantee gì; vì sao side effect `AFTER_COMMIT` thất bại vẫn cần outbox hoặc retry bền vững?

### JVM-073 [Senior · ⭐ Rất thường gặp] Thiết kế POST idempotent trong Spring REST bằng `Idempotency-Key` thế nào để xử lý concurrent duplicate, payload mismatch, response replay, TTL và transaction boundary?

**Kết luận:** Scope key theo principal/tenant + operation, lưu request fingerprint, trạng thái và response/result; unique constraint làm đúng một request giành quyền thực thi, duplicate cùng payload chờ/đọc lại kết quả.

**Cơ chế:** Trong transaction phù hợp, insert key `IN_PROGRESS` và commit business effect + completed result atomically hoặc dùng state machine/outbox cho external effect. Cùng key khác fingerprint phải reject; TTL dài hơn retry horizon và cleanup không xóa key còn effect có thể replay.

```sql
UNIQUE (tenant_id, operation, idempotency_key)
```

**Pitfall / follow-up Senior:** Giữ DB lock trong lúc gọi provider làm nghẽn; cần lease/recovery cho owner crash và response replay không chứa credential hết hạn. Idempotency không thay authorization, rate limit hay provider reconciliation.
